# 1. Мета, завдання та очікувані результати

Метою самостійної роботи є створення не формального переліку вимог до оформлення коду, а практичного документа команди, за яким декілька розробників можуть спільно підтримувати проєкт протягом тривалого часу. Такий документ має допомагати приймати однакові рішення, зменшувати кількість дефектів, прискорювати code review і не допускати ситуації, коли правила залежать від особистих звичок конкретного програміста.

У межах роботи стандарт сформовано для навчального проєкту `LibraryDesk`, який моделює каталог бібліотеки та процес видачі книжок читачам. Проєкт має бібліотеку предметної логіки `LibraryDesk.Core` і консольний застосунок `LibraryDesk.App`. Саме тому правила були адаптовані до реальних сутностей цього проєкту, а не записані як загальна копія рекомендацій для C#.

# 2. Опис проєкту та предметної області

## 2.1. Загальна характеристика LibraryDesk

`LibraryDesk` — навчальний проєкт для обліку книжкового фонду, читачів і видачі книжок. Його основна задача полягає в тому, щоб зберігати інформацію про книги, читачів і документи видачі, а також виконувати базові операції над цими об’єктами.

Проєкт складається з двох логічних частин:

| Проєкт | Призначення | Дозволені залежності |
|---|---|---|
| `LibraryDesk.Core` | моделі й предметна логіка | базові бібліотеки .NET |
| `LibraryDesk.App` | консольний інтерфейс | `LibraryDesk.Core`, Console API |

Розділення важливе для якості коду. Бізнес-логіка не повинна залежати від `Console.ReadLine`, `Console.WriteLine`, формату виводу або конкретного способу введення даних. Якщо логіку можна викликати без консолі, її простіше тестувати, повторно використовувати та перенести в інший інтерфейс.

## 2.2. Основні сутності

У проєкті використовуються такі основні типи:

### `Book`

`Book` описує книгу бібліотечного фонду. Вона має ISBN, назву, добовий тариф прокату та кількість доступних примірників.

Приклад властивостей:

```csharp
public sealed class Book
{
    public string Isbn { get; init; } = string.Empty;
    public string Title { get; init; } = string.Empty;
    public decimal RentalFee { get; init; }
    public int AvailableCopies { get; init; }
}
```

### `Reader`

`Reader` — читач бібліотеки. Він має ідентифікатор, повне ім’я та ознаку активного членства.

```csharp
public sealed class Reader
{
    public int Id { get; init; }
    public string FullName { get; init; } = string.Empty;
    public bool HasActiveMembership { get; init; }
}
```

### `Loan`

`Loan` — документ, який фіксує факт видачі книг читачеві. Він містить ідентифікатор читача, дату видачі, статус і колекцію позицій.

### `LoanItem`

`LoanItem` — одна позиція документа видачі. Вона пов’язує ISBN книги, кількість днів користування і добову ставку.

### `LoanStatus`

`LoanStatus` описує життєвий цикл документа. У проєкті використовуються стани `Active`, `Returned`, `Overdue`, `Cancelled` і `Lost`.

## 2.3. Чому стандарт залежить від предметної області

Загальні конвенції C# не відповідають на всі питання, які виникають у конкретному проєкті. Наприклад, вони можуть рекомендувати використовувати зрозумілі імена, але не визначають, чи називати сутність читача `Reader`, `User`, `Client` або `Member`. Вони не визначають, чи кінцева дата видачі входить до строку, і не пояснюють, коли саме книга вважається простроченою.

Для `LibraryDesk` ці рішення важливіші за косметичне форматування. Якщо один розробник вважає, що `DueDate` — це останній дозволений день, а інший — що це перший день прострочення, у системі з’явиться помилка на межі періоду. Тому стандарт фіксує не лише форму коду, а й терміни, типи даних та правила предметної логіки.

# 3. Проблема, яку вирішує стандарт команди

## 3.1. Вартість відсутності домовленостей

Якщо команда не має стандарту, кожен розробник приймає однакові рішення самостійно. Наприклад:

- один називає читача `Reader`, інший — `User`;
- один зберігає дату як `DateTime`, інший — як рядок;
- один повертає `List<LoanItem>`, інший — `IReadOnlyList<LoanItem>`;
- один використовує `double` для тарифів, інший — `decimal`;
- один вважає 13 жовтня останнім днем видачі, інший — першим днем прострочення;
- один округлює кожну позицію, інший — тільки підсумок.

Кожне окреме рішення може здаватися незначним. Проте в сукупності вони створюють витрати:

1. Читач коду витрачає час на розшифрування термінів.
2. Code review перетворюється на суперечку про особисті вподобання.
3. Пошук по репозиторію перестає бути надійним.
4. Тести стають складнішими через прихований системний час або неправильні типи.
5. Дефекти виявляються не під час компіляції, а в роботі програми.

## 3.2. Принципи, покладені в основу стандарту

Стандарт LibraryDesk базується на таких принципах:

| Принцип | Практичне значення |
|---|---|
| Ясність важливіша за стислість | `overdueLoanCount` краще за `n` |
| Тип має виражати бізнес-сенс | `LoanStatus` краще за `int status` |
| Машина повинна перевіряти повторювані правила | форматування не обговорюють вручну |
| Людина перевіряє предметний зміст | аналізатор не знає, чи правильно визначено прострочення |
| Правило має бути перевірним | для кожного правила вказано спосіб контролю |
| Винятки мають бути явними | suppression дозволено тільки з обґрунтуванням |
| Зміни стандарту мають бути оборотними | рішення фіксуються в журналі |

## 3.3. Чому всі правила не зроблено обов’язковими

Якщо команда оголосить абсолютно кожну пораду обов’язковою, документ стане надто жорстким. Розробники почнуть ігнорувати його цілком або додавати бездумні придушення аналізаторів. Тому обов’язковими зроблено переважно ті правила, які:

- усувають реальний дефект;
- стабілізують публічний контракт;
- можуть бути перевірені машиною;
- важливі для тестування;
- залежать від однозначності предметної області.

Рекомендації залишено для рішень, де контекст може мати значення. Наприклад, порядок статичних методів або вибір між двома читабельними способами декомпозиції не завжди повинен зупиняти збірку.

# 4. Сфера дії та рівні обов’язковості

## 4.1. Сфера дії

Стандарт діє для всіх C#-файлів, які підтримуються командою LibraryDesk:

- доменних сутностей у `LibraryDesk.Core`;
- сервісів і репозиторіїв, які будуть додані пізніше;
- консольної взаємодії у `LibraryDesk.App`;
- автоматизованих тестів;
- прикладів коду, які компілюються разом із рішенням.

Стандарт не поширюється на:

- `bin/` і `obj/`;
- згенеровані файли;
- тимчасові експерименти в гілці `sandbox`;
- сторонній код, який підключено як бібліотеку;
- файли, що генеруються інструментом і не редагуються вручну.

## 4.2. Власник стандарту

Власником стандарту є команда проєкту. У навчальному репозиторії фактичну відповідальність за актуальність документа несе автор роботи, але запропонована процедура розрахована на команду з чотирьох-п’яти розробників.

Власник не може одноосібно змінювати правило без пояснення. Його обов’язки:

1. стежити за узгодженістю `CODING_STANDARD.md`, `.editorconfig` і `Directory.Build.props`;
2. перевіряти, що нове правило має ID і спосіб перевірки;
3. підтримувати журнал рішень;
4. видаляти застарілі або суперечливі формулювання;
5. контролювати перехідний період після зміни стандарту.

## 4.3. Рівні обов’язковості

| Рівень | Значення | Наслідок порушення |
|---|---|---|
| ОБОВ’ЯЗКОВО | виконується завжди | build падає або PR не приймається |
| РЕКОМЕНДОВАНО | виконується без вагомої причини відступити | зауваження в code review |
| ДОПУСКАЄТЬСЯ | дозволено два рівноцінні варіанти | зауваження не робиться |
| ЗАБОРОНЕНО | конструкція не використовується | build падає або зміна відхиляється |

Для рекомендованого правила відступ допустимий, якщо в pull request записано коротке пояснення. Якщо це системне рішення, воно має бути винесене в журнал рішень, а не залишене лише в коментарі до конкретного рядка.

## 4.4. Нумерація правил

Правила мають префікси:

- `N` — naming, іменування;
- `F` — formatting, форматування;
- `C` — comments, коментарі й документація;
- `D` — data, дані й типи;
- `S` — statements, керування і складність;
- `A` — automation, машинна перевірка;
- `X` — специфічні правила LibraryDesk.

Наприклад, code review може містити конкретне зауваження: «Порушено `X-02`: `DueDateExclusive` треба порівнювати через `>=`, оскільки це перший день прострочення». Таке зауваження значно корисніше, ніж «Дата обробляється неправильно».

## 5.3. Правила використання термінів

Термін `Reader` використовується для особи, яка має читацький профіль. Термін `User` у доменній логіці не використовується, бо він занадто загальний і може позначати оператора системи, адміністратора або читача.

Термін `Loan` використовується для документа видачі, а не для самої дії. Метод `CreateLoan` створює документ, `ReturnLoan` реєструє повернення, `MarkAsOverdue` змінює статус після перевірки дати.

Термін `DueDateExclusive` спеціально містить суфікс `Exclusive`. Звичайне ім’я `DueDate` не повідомляє, чи включено цей день до дозволеного строку. У цьому проєкті вибрано напіввідкритий інтервал `[start, end)`, тому кінець не входить до дозволеного періоду.

# 6. Стандарт іменування ідентифікаторів

## 6.1. Загальні правила

Імена мають відповідати поняттям предметної області, бути придатними для пошуку і не вимагати коментаря для розшифрування. Коментар не може бути виправданням поганого імені.

Коротке ім’я дозволено тільки тоді, коли воно є загальноприйнятим у контексті:

- `Id` — ідентифікатор;
- `Isbn` — ISBN у форматі C#-ідентифікатора;
- `i` — лічильник короткого циклу;
- `x` і `y` — координати, якщо метод явно працює з геометрією.

## 6.2. Таблиця іменування

| Вид ідентифікатора | Правило | Приклад |
|---|---|---|
| namespace | PascalCase, корінь `LibraryDesk` | `LibraryDesk.Core.Domain` |
| class | PascalCase, іменник | `LoanItem` |
| record | PascalCase, поняття-значення | `LoanPeriod` |
| interface | `I` + PascalCase | `ILoanRepository` |
| enum | PascalCase, однина | `LoanStatus` |

### Приклад 1: метод

```csharp

    foreach (var x in l)
```

# 7. Форматування та структура файлів

## 7.1. Відступи

Для C# використовується чотири пробіли на один рівень. Табуляції заборонені. Для XML, JSON і MSBuild-файлів використовується два пробіли. Це відповідає загальному стилю .NET і забезпечує однакове відображення у різних редакторах.

## 7.2. Довжина рядка

Максимальна довжина рядка — 100 символів. Це не твердження, що довший рядок завжди неправильно працює. Це обмеження для зручності огляду: на екрані шириною 1920 пікселів код можна читати у двох колонках під час порівняння версій без постійного горизонтального прокручування.

Якщо вираз довший, його переносять на логічні частини:

```csharp
bool isValidLoan = loan is not null
    && loan.Items.Count > 0
    && loan.Status == LoanStatus.Active;
```

Перенесення не повинно створювати приховану зміну пріоритету операторів. За потреби використовуються дужки.

## 7.3. Фігурні дужки

Використовується стиль Allman: відкривна дужка розміщується на новому рядку. Дужки обов’язкові навіть для одного оператора:

```csharp
if (reader.HasActiveMembership)
{
    return true;
}
```

Команда свідомо посилює це правило. Код без дужок коротший лише на один рядок, але додавання другого оператора під час поспішної зміни може створити дефект, який не видно з візуального відступу.

## 7.4. Простір імен і using

Використовується file-scoped namespace:

```csharp
namespace LibraryDesk.Core.Domain;
```

Директиви `using` розміщуються на початку файла. Системні простори імен — перед просторами імен проєкту. Невикористані using видаляються.

## 7.5. Порядок членів класу

Рекомендований порядок:

1. константи;
2. статичні поля;
3. приватні поля екземпляра;
4. конструктори;
5. public properties;
6. події;
7. public methods;
8. private methods.

Мета порядку — не естетика, а швидке орієнтування в типі. Читач спочатку бачить сталі обмеження, потім внутрішній стан, а після цього публічний контракт.

## 7.6. Файл і тип

Один файл має містити один головний public тип. `Loan.cs` містить `Loan`, `LoanStatus.cs` — `LoanStatus`. Виняток можливий для тісно пов’язаних приватних допоміжних типів, але він пояснюється в code review.

## 7.7. Заборона region

`#region` не використовується для приховування частин великого класу. Якщо тип потребує багато регіонів, це сигнал перевірити відповідальності та виділити декілька менших типів.

# 8. Коментарі й XML-документація

## 8.1. Коментар «що» і коментар «чому»

Коментар не повинен повторювати синтаксис:

```csharp
// Погано: збільшуємо days на один.
days++;
```

Корисний коментар пояснює бізнес-рішення:

```csharp
// Кінцева дата виключна: день, записаний у DueDateExclusive,
// уже не входить до дозволеного строку.
return today < DueDateExclusive;
```

Такий коментар потрібен, тому що з одного оператора `<` не видно, чому використано саме його, а не `<=`.

## 8.2. Заборонені коментарі

Заборонено:

- залишати закоментований код замість Git-історії;
- дублювати очевидний код;
- виправдовувати коментарем погане ім’я;
- залишати коментар, який суперечить реалізації;
- додавати `TODO` без номера задачі й автора;
- пояснювати тип замість використання зрозумілого типу.

## 8.3. XML-документація

Усі публічні типи й члени бібліотеки `LibraryDesk.Core` мають XML-документацію. Мінімальні теги:

- `<summary>` — призначення типу або члена;
- `<param>` — сенс параметра;
- `<returns>` — значення, яке повертається;
- `<exception>` — виняток, який метод свідомо викидає;
- `<remarks>` — додаткові інваріанти або важливі обмеження;
- `<see cref="..."/>` — посилання на пов’язаний тип.

Приклад:

```csharp
/// <summary>
/// Перевіряє, чи є видача простроченою на вказану календарну дату.
/// Метод не змінює стан документа.
/// </summary>
/// <param name="today">Дата, на яку виконується перевірка.</param>
/// <returns>
/// <see langword="true"/>, якщо дата не менша за DueDateExclusive.
/// </returns>
public bool IsOverdueOn(DateOnly today)
{
    return today >= DueDateExclusive;
}
```

Властивість `GenerateDocumentationFile` увімкнено в `Directory.Build.props`. Рівень `CS1591` встановлено як warning, а `TreatWarningsAsErrors` перетворює його на помилку під час збірки.

# 9. Дані, типи, гроші та час

## 9.1. Nullable

Nullable reference types увімкнено. Якщо значення не може бути null, це видно з типу та ініціалізації. Якщо null є частиною контракту, це записується в типі через `?` і пояснюється XML-документацією.

Оператор `!` не використовується як спосіб приховати попередження. Він допускається тільки тоді, коли інваріант доведено зовнішньою перевіркою й над рядком є обґрунтування.

## 9.2. Змінні

Змінна оголошується якомога ближче до першого використання. Не слід повторно використовувати одну змінну для різних сутностей:

```csharp
// Погано: value спочатку є кількістю, потім сумою.
int value = item.Days;
value = (int)item.Amount;
```

```csharp
// Добре.
int loanDays = item.Days;
decimal itemAmount = item.Amount;
```

Це допомагає не переносити випадково неправильне значення між частинами методу.

## 9.3. Константи

Числові та рядкові літерали в логіці замінюються іменованими константами. Виняток — очевидні `0`, `1`, `-1`, порожній рядок і значення, які є частиною синтаксичної операції.

```csharp
private const int DefaultLoanDays = 14;
private const int MaximumLoanDays = 30;
private const decimal LateFeePerDay = 5.00m;
```

`const` використовується для справді незмінного значення, відомого під час компіляції. `static readonly` використовується, якщо значення обчислюється під час запуску або має складний тип.

Enum використовується замість набору числових кодів, коли значення є закритою множиною станів. Конфігурація використовується тоді, коли значення може змінитися без перекомпіляції, наприклад ставка штрафу в різних філіях.

## 9.4. Вибір колекції

| Ситуація | Тип |
|---|---|
| упорядкована послідовність для читання | `IReadOnlyList<T>` |
| множина без дублювання | `HashSet<T>` |
| пошук за ключем | `Dictionary<TKey, TValue>` |
| внутрішній змінний список | `List<T>` |
| public API без дозволу змін | `IReadOnlyCollection<T>` |

Тип у public API описує не конкретну реалізацію, а можливості клієнта. Якщо метод тільки читає позиції, він не має вимагати `List<LoanItem>` без потреби.

## 9.5. Гроші

Усі грошові значення `RentalFee`, `DailyRate`, `Amount`, штрафи та підсумки мають тип `decimal`. `double` і `float` заборонені для грошей через бінарне представлення дробів.

```csharp
decimal dailyRate = 19.99m;
decimal amount = dailyRate * days;
```

Суфікс `m` обов’язковий для decimal-літералів. Без суфікса `19.99` має тип `double`, після чого неявне перетворення приховує намір автора.

Округлення виконується до двох знаків із `MidpointRounding.AwayFromZero` і один раз на підсумку документа:

```csharp
decimal total = Math.Round(
    subtotal,
    2,
    MidpointRounding.AwayFromZero);
```

Округлення кожної позиції окремо може дати суму, відмінну від округлення загальної суми. Для звіту і чека це створює реальну розбіжність.

## 9.6. Дати, моменти й тривалості

| Значення | Тип | Приклад |
|---|---|---|
| календарна дата без часу | `DateOnly` | `DueDateExclusive` |
| момент у часовій шкалі | `DateTimeOffset` | `IssuedAt` |
| час доби | `TimeOnly` | час відкриття філії |
| тривалість | `TimeSpan` | тривалість операції |

`DateTime.Now` у `LibraryDesk.Core` заборонений, оскільки робить метод залежним від машини та моменту запуску. Для тестування поточний час передається через `TimeProvider` або власний `IClock`.

# 10. Спеціальний акцент варіанта: строки видачі та прострочення

## 10.1. Напіввідкриті інтервали

Для строку видачі використовується інтервал `[start, end)`: початок включено, кінець виключено. Якщо книгу видано 06.10 на сім календарних днів, дозволений період містить 06.10, 07.10, 08.10, 09.10, 10.10, 11.10 і 12.10. Дата 13.10 є першим днем прострочення.

Щоб уникнути двозначності, у моделі зберігається `DueDateExclusive = 13.10`. Перевірка має вигляд:

```csharp
public bool IsOverdueOn(DateOnly today)
{
    return today >= DueDateExclusive;
}
```

Якщо команда зберігає останній дозволений день, потрібна була б умова `today > lastAllowedDate`. Вибір `Exclusive` робить формулу однаковою для всіх строків і зручним розрахунок наступного періоду.

## 10.2. Розділення моменту і календарної дати

`IssuedAt` і `DueDateExclusive` не можна замінити одним `DateTime`. `IssuedAt` фіксує конкретний момент, потенційно з часовим поясом. `DueDateExclusive` описує день календаря, а не момент у UTC.

Поганий приклад:

```csharp
public DateTime IssuedAt { get; init; }
public DateTime DueDate { get; init; }

public bool IsOverdue()
{
    return DateTime.Now > DueDate;
}
```

Недоліки:

1. `DateTime` не пояснює, чи значення локальне, UTC або невизначене.
2. `DateTime.Now` неможливо стабільно перевірити тестом.
3. Порівняння залежить від часу доби.
4. Невідомо, чи входить дата повернення до строку.

Добрий варіант:

```csharp
public DateTimeOffset IssuedAt { get; init; }
public DateOnly DueDateExclusive { get; init; }

public bool IsOverdueOn(DateOnly today)
{
    return today >= DueDateExclusive;
}
```

## 10.3. Граничні тести

Для правила X-02 необхідні щонайменше такі тести:

| Сценарій | `today` | `DueDateExclusive` | Очікування |
|---|---|---|---|
| день перед межею | 12.10 | 13.10 | `false` |
| перший день прострочення | 13.10 | 13.10 | `true` |
| кілька днів після | 15.10 | 13.10 | `true` |
| дата видачі | 06.10 | 13.10 | `false` |
| від’ємний строк | 06.10 | 05.10 | виняток під час створення |
| нульовий строк | 06.10 | 06.10 | або заборонено моделлю, або одразу прострочено за явним рішенням |

Стандарт обирає заборону нульового строку для звичайної видачі. Це краще, ніж дозволити неповний документ, а потім обробляти його різними способами в сервісах.

## 10.4. Округлення та строк

Строк видачі є цілим числом календарних днів, тому `Days` має тип `int`. Тариф за день і сума мають тип `decimal`. Не можна зберігати кількість днів у `decimal`, якщо частковий день не передбачений предметною областю.

Якщо в майбутньому з’явиться погодинний прокат, це буде зміна предметної моделі. Тоді потрібно ввести окрему одиницю, наприклад `TimeSpan`, а не почати передавати дробове число в наявне поле `Days`.

# 11. Керуючі конструкції та межі складності

## 11.1. Guard clauses

Невалідні аргументи перевіряються на початку методу:

```csharp
public decimal CalculateTotal(Loan loan)
{
    ArgumentNullException.ThrowIfNull(loan);

    decimal total = 0m;
    foreach (LoanItem item in loan.Items)
    {
        total += item.Amount;
    }

    return total;
}
```

Поганий стиль — обгортати всю логіку в декілька рівнів `if`. Він збільшує когнітивне навантаження і може перетворити помилкові дані на нормальний, але неправильний результат.

## 11.2. Вибір між if і switch

Для двох простих взаємовиключних умов достатньо `if`. Для повної множини станів використовується `switch` або switch expression:

```csharp
string GetStatusLabel(LoanStatus status)
{
    return status switch
    {
        LoanStatus.Active => "Активна",
        LoanStatus.Returned => "Повернено",
        LoanStatus.Overdue => "Прострочено",
        LoanStatus.Cancelled => "Скасовано",
        LoanStatus.Lost => "Втрачено",
        _ => throw new ArgumentOutOfRangeException(nameof(status)),
    };
}
```

Перевага — компілятор і рев’ю допомагають побачити пропущений стан.

## 11.3. Цикли

`foreach` використовується для обходу колекції, коли індекс не потрібен. `for` дозволено, коли потрібна позиція елемента або керування кроком.

Колекцію не можна змінювати під час обходу:

```csharp
// Погано: InvalidOperationException.
foreach (LoanItem item in loan.Items)
{
    loan.RemoveItem(item);
}
```

Краще спочатку сформувати список для видалення, а потім змінити колекцію, або використовувати операцію самого агрегата, яка гарантує коректність.

## 11.4. Числові межі

| Метрика | Warning | Error | Дія |
|---|---:|---:|---|
| цикломатична складність методу | 8 | 12 | виділити метод |
| глибина вкладеності | 3 | 4 | guard clause/decomposition |
| рядки в методі | 30 | 50 | декомпозиція |
| параметри методу | 4 | 6 | object parameter |
| public members класу | 12 | 20 | виділити тип |
| рядки у файлі | 300 | 500 | розділити файл/тип |

## 11.5. Ручний розрахунок цикломатичної складності

Цикломатична складність для одного методу визначається як:

```text
M = 1 + кількість незалежних умов і розгалужень
```

Розглянемо метод, який перевіряє видачу:

```csharp
public bool CanReturn(Loan loan, Reader reader, DateOnly today)
{
    if (loan is null)
    {
        return false;
    }

    if (reader is null)
    {
        return false;
    }

    if (!reader.HasActiveMembership)
    {
        return false;
    }

    if (loan.Status == LoanStatus.Cancelled)
    {
        return false;
    }

    if (loan.Status == LoanStatus.Returned)
    {
        return false;
    }

    if (today < loan.IssuedAt.Date)
    {
        return false;
    }

    return true;
}
```

У методі шість умов `if`. Отже:

```text
M = 1 + 6 = 7
```

Результат 7 нижчий за warning-поріг 8, але метод уже близький до межі. Якщо додати перевірку на наявність позицій, допустимість статусу `Lost` і валідність дати, отримаємо 10, що вимагає обговорення та, ймовірно, виділення методів `HasValidReader`, `HasReturnableStatus` і `IsDateValid`.

Приклад складнішого методу з дев’ятьма незалежними умовами:

```text
M = 1 + 9 = 10
```

Такий метод не заборонений миттєво, але має бути розділений, якщо всі перевірки не утворюють одну природну операцію.

```csharp
private readonly List<LoanItem> _items = new();
```

# 14. Чекліст огляду коду

## 14.1. Чому чекліст не дублює аналізатори

Машина добре перевіряє форму: пробіли, дужки, частину naming, відсутність XML-коментаря. Але вона не розуміє, чи коректно визначено предметну логіку. Аналізатор не знає, чи треба включати день повернення у строк, чи є метод надто широким за відповідальністю, чи тест перевіряє важливу межу.

Тому чекліст містить людські питання.

## 14.2. Групи перевірки

### Іменування та модель

1. Чи відповідають назви термінам глосарія?
2. Чи можна зрозуміти призначення методу без читання всього тіла?
3. Чи не використано загальні слова `data`, `info`, `helper`?
4. Чи не змішані `Reader`, `User` і `Client` для одного поняття?

### Дані й типи

5. Чи використано `decimal` для грошей?
6. Чи не захований стан документа у числовому або рядковому полі?
7. Чи не використовується `DateTime` там, де потрібен `DateOnly`?
8. Чи не читає Core системний годинник?
9. Чи захищено public колекцію від зовнішньої зміни?

### Предметні межі

10. Чи однозначно визначено `DueDateExclusive`?
11. Чи перевірено день перед межею і саму межу?
12. Чи відхиляється нульовий або від’ємний строк?
13. Чи не змішані часовий момент і календарний день?

### Помилки й побічні ефекти

14. Чи не маскується помилка нульовим результатом?
15. Чи не проковтується виняток у порожньому `catch`?
16. Чи зрозуміло з назви, що метод змінює стан?
17. Чи документовано свідомі винятки?

### Тести

18. Чи є тест на кожну нову гілку?
19. Чи є тест на граничну дату?
20. Чи є негативний тест на недійсний статус або строк?

### Культура огляду

21. Зауваження формулюється щодо коду, а не особи.
22. Зауваження містить конкретну дію.
23. Непевне побажання не маскується під обов’язкове правило.

## 14.3. Приклади якісних зауважень

Невдале зауваження: «Незрозуміло». Воно не дає автору дії.

Якісне зауваження: «Порушено X-02: замініть `today > DueDateExclusive` на `today >= DueDateExclusive`, оскільки `DueDateExclusive` є першим днем прострочення. Додайте тест для дати, рівної межі».

Невдале зауваження: «Тут неправильний тип».

Якісне зауваження: «Порушено D-05: замініть `double DailyRate` на `decimal DailyRate`, додайте суфікс `m` для літерала і перевірте округлення підсумку».

## 15.4. Свідомі відмінності

### Дужки

`dotnet/runtime` допускає блок без дужок для окремої інструкції за певних умов. LibraryDesk вимагає дужки завжди. Причина — навчальна команда часто змінює короткі умови, і найтиповіша помилка полягає в додаванні другого рядка без дужок. Вартість правила — один рядок; вартість дефекту може бути значно більшою.

### Довжина рядка

`dotnet/runtime` не встановлює жорсткої межі для всього коду. LibraryDesk встановлює 100 символів, тому що навчальний репозиторій часто переглядають у двох колонках. Це не абсолютне правило читабельності, а стабільне обмеження для diff.

### Предметні дати

Публічні стилі не можуть визначити семантику строку саме бібліотеки. LibraryDesk додає `DueDateExclusive`, `DateOnly` і метод `IsOverdueOn(today)`, бо прострочення залежить від календарної межі, а не від стилю C#.

# 16. Журнал рішень і порядок зміни стандарту

## 16.1. ADR-001: напіввідкритий строк видачі

Рішення: кінцева дата не входить до дозволеного періоду, а `DueDateExclusive` означає перший день прострочення.

Обґрунтування: напіввідкриті інтервали добре компонуються, не створюють подвійного рахунку днів і дозволяють використовувати одну умову `today >= end`.

Наслідок: потрібні `DateOnly`, суфікс `Exclusive` і граничні тести.

## 16.2. ADR-002: приватні поля з підкресленням

Рішення: instance-поля мають `_camelCase`, static-поля — `s_camelCase`.

Обґрунтування: префікс відрізняє поле від параметра і локальної змінної. Це дозволяє не використовувати `this.` лише для зняття неоднозначності.

Наслідок: `SA1309` вимкнено із поясненням, а naming rule Roslyn має рівень error.

## 16.3. Процедура внесення зміни

1. Будь-який учасник створює пропозицію у pull request.
2. Пропозиція містить ID, текст правила, рівень, обґрунтування, приклади, спосіб машинної перевірки та оцінку вартості міграції.
3. Автор додає хоча б один приклад дефекту, який правило запобігає.
4. Двоє інших учасників перевіряють, чи не дублює правило наявне.
5. Рішення ухвалюється більшістю команди.
6. Власник оновлює `CODING_STANDARD.md`, `.editorconfig` і за потреби `Directory.Build.props`.
7. Рішення отримує номер і дату у `DECISIONS.md`.
8. Для зміни рівня обов’язковості підвищується major-версія.
9. Для нового необов’язкового правила підвищується minor-версія.
10. Для редакційного уточнення підвищується patch-версія.
11. Наявний код не переписується одномоментно без оцінки; діє перехідний період 14 днів.
12. Застосовується правило бойскаута: змінений файл залишають чистішим.
13. Шкідливе правило скасовується окремим ADR із поясненням і тестом на причину скасування.

# 17. Підготовка до захисту

## 17.1. Демонстрація репозиторію

Під час захисту можна показати послідовність:

1. Відкрити `CODING_STANDARD.md` і показати сферу дії, рівні та глосарій.
2. Перейти до X-правил і пояснити `DueDateExclusive`.
3. Показати `.editorconfig` і `Directory.Build.props`.
4. Пояснити, чому гроші мають `decimal`, а поточний час не читається через `DateTime.Now`.
5. Показати чекліст і пояснити, чому він не дублює аналізатори.
6. Відкрити `DECISIONS.md` і показати ADR-001 та ADR-002.
7. Продемонструвати навмисне порушення naming rule.
8. Запустити `dotnet build -warnaserror` після виправлення.

## 17.2. Орієнтовні відповіді на запитання

**Чому не всі правила мають рівень ОБОВ’ЯЗКОВО?**  
Тому що надмірна кількість жорстких правил призводить до ігнорування стандарту. Обов’язковими зроблено правила, які усувають дефекти або стабілізують контракт.

**Чому `DateOnly`, а не `DateTime`?**  
Строк видачі є календарним поняттям. Час доби не повинен змінювати факт прострочення, тому дата й момент розділені.

**Чому `DueDateExclusive`?**  
Суфікс повідомляє, що це перший день, який не входить до дозволеного періоду. Тому перевірка прострочення має `>=`.

**Чому `decimal`, а не `double`?**  
Гроші потребують десяткової арифметики й передбачуваного округлення. `double` може зберігати десяткові дроби з бінарною похибкою.

**Що перевіряє машина, а що людина?**  
Машина перевіряє формат, naming, дужки, документацію та warning-и. Людина перевіряє предметний зміст, межі періодів, побічні ефекти, якість тестів і відповідність зміни задачі.

**Що робити, якщо метод природно має вісім гілок?**  
Поріг 8 є попередженням, а не автоматичною забороною. Треба оцінити, чи це одна природна операція; якщо так, залишити з тестами, а якщо ні — виділити методи.

# 18. Висновки

У результаті виконання самостійної роботи створено цілісний стандарт кодування для проєкту `LibraryDesk`. Він охоплює іменування, форматування, структуру файлів, коментарі, XML-документацію, вибір типів, роботу з грошима, датами та станами документів.

Найважливішою предметною частиною є правило строків видачі. Для нього розділено момент видачі `DateTimeOffset` і календарну межу `DateOnly`, визначено напіввідкритий інтервал і зафіксовано формулу `today >= DueDateExclusive`. Це прибирає неоднозначність на першому дні прострочення й дозволяє писати детерміновані тести.

Стандарт підкріплено машинною частиною. `.editorconfig` відповідає за стиль і naming, `Directory.Build.props` — за nullable, аналізатори, XML-документацію та строгий режим збірки. Навмисне порушення naming rule показує, що документ є виконуваною домовленістю, а не лише теоретичним текстом.

Чекліст code review доповнює аналізатори, зосереджуючись на предметній логіці, граничних випадках, побічних ефектах і тестах. Журнал рішень забезпечує історію спірних домовленостей, а процедура зміни стандарту не дозволяє непомітно змінювати правила протягом семестру.

Окремий запис `TD-001` у `TECHNICAL_DEBT.md` пояснює suppression `CA1305` для успадкованого `Order.cs`. У записі вказано причину, відповідального, план погашення і статус, тому suppression не є прихованою зміною стандарту.

Отже, комплект придатний для подальшого використання в лабораторних роботах: новий код можна перевіряти автоматично, а зміни предметної логіки — системно обговорювати на code review.
