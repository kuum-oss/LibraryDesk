# Стандарт кодування проєкту LibraryDesk

Цей документ фіксує обов'язкові інженерні домовленості та правила розробки навчального проєкту **LibraryDesk** (Варіант № 2 — облік видачі книг у бібліотеці) у межах курсу «Конструювання програмного забезпечення».

---

## 1. Загальні положення

1. Даний стандарт є обов'язковим для всіх учасників розробки та діє впродовж усіх лабораторних робіт.
2. Будь-яке правило, яке можна закріпити автоматично, закріплюється машинно через `.editorconfig`, правила компілятора Roslyn та правила StyleCop.
3. Код, що генерує хоча б одне попередження (`warning`) компілятора чи аналізатора, вважається дефектним і не приймається до репозиторію.
4. Проєкт націлено на платформу **.NET 8** із використанням найновіших можливостей синтаксису C# (`LangVersion = latest`).
5. Увімкнено механізм перевірки посилань на `null` (`Nullable = enable`). Використання оператора придушення `!` без вагомого обґрунтування заборонене.

## 2. Правила іменування (Naming Conventions)

Іменування сутностей має однозначно відображати їхнє призначення в предметній області бібліотечної справи. Скорочення заборонені (винятки: `Id`, `Isbn`).

| Сутність | Конвенція | Приклад | Антиприклад |
| :--- | :--- | :--- | :--- |
| **Клас (Class)** | `PascalCase`, іменник | `LoanItem`, `Reader` | `loanItem`, `cReader` |
| **Запис (Record)** | `PascalCase`, іменник | `BookDetails` | `book_record` |
| **Інтерфейс (Interface)** | `I` + `PascalCase`, прикметник/іменник | `ILoanRepository` | `LoanRepositoryInterface`, `LoanRepo` |
| **Метод (Method)** | `PascalCase`, дієслово або дієслівна фраза | `CalculateTotal`, `AddItem` | `calc`, `doProcess` |
| **Властивість (Property)** | `PascalCase`, іменник/прикметник | `DailyRate`, `Status` | `get_DailyRate`, `RateVal` |
| **Булева властивість** | `PascalCase`, префікс `Is` / `Has` / `Can` | `HasActiveMembership` | `ActiveMember`, `Flag` |
| **Приватне поле екземпляра** | `_` + `camelCase` | `_items`, `_logger` | `m_items`, `items`, `_Items` |
| **Локальна змінна** | `camelCase`, осмислена назва | `totalAmount`, `activeLoans` | `ta`, `tmp`, `val` |
| **Параметр методу** | `camelCase` | `loanItem`, `readerId` | `Item`, `p_readerId` |
| **Константа (`const`)** | `PascalCase` | `MaxLoanPeriodDays` | `MAX_DAYS`, `max_loan_period` |
| **Статичне поле лише для читання** | `PascalCase` | `DefaultDailyRate` | `s_defaultDailyRate` |
| **Перелічення (Enum)** | `PascalCase`, іменник в однині | `LoanStatus` | `LoanStatuses`, `ELoanStatus` |
| **Елемент перелічення** | `PascalCase` | `Active`, `Returned` | `ACTIVE`, `loan_active` |
| **Простір імен (Namespace)** | `PascalCase`, ієрархічний | `LibraryDesk.Core.Domain` | `library_desk_core` |

## 3. Правила форматування коду (Code Formatting)

Форматування стандартизується машинно з чіткими числовими та синтаксичними обмеженнями:

1. **Відступи**: рівно **4 пробіли** для файлів C# (`.cs`); використання символу табуляції (`\t`) **суворо заборонено**.
2. **Конфігураційні файли**: для файлів XML (`.csproj`, `.props`, `.targets`), JSON та YAML розмір відступу становить **2 пробіли**.
3. **Довжина рядка**: не більше ніж **100 символів**. Рядки більшої довжини мають переноситися на наступний рядок із логічним відступом.
4. **Стиль фігурних дужок (Allman)**: відкривна дужка `{` завжди розміщується на новому рядку на тому ж рівні відступу, що й оголошення інструкції/типу.
5. **Обов'язковість дужок**: блоки інструкцій `if`, `else`, `for`, `foreach`, `while`, `do` завжди обмежуються фігурними дужками, навіть якщо тіло містить лише одну інструкцію.
6. **Порожні рядки**: між членами типу (методами, властивостями, конструкторами) має бути **рівно один порожній рядок**. Заборонено більше одного порожнього рядка поспіль.
7. **Символи кінця рядків**: усі файли мають завершуватися одним символом нового рядка (`insert_final_newline = true`), зайві пробіли на кінцях рядків мають видалятися автоматично (`trim_trailing_whitespace = true`).
8. **Організація простору імен**: використовується синтаксис простору імен файлового рівня (`namespace LibraryDesk.Core.Domain;`), без додаткових відступів і фігурних дужок на весь файл.
9. **Директиви `using`**: розміщуються виключно на початку файлу перед простором імен, сортуються за алфавітом, при цьому системні простори імен (`System.*`) завжди розміщуються першими. Невживані директиви підлягають негайному видаленню.

## 4. Коментарі та документація

Коментарі мають пояснювати причину архітектурного чи алгоритмічного рішення («чому так зроблено»), а не переказувати очевидну роботу інструкцій («що саме робить код»).

### 4.1. Приклади «Погано — Добре»

```csharp
// ПОГАНО: коментар переказує код
// збільшуємо лічильник днів на одиницю
loanDays = loanDays + 1;

// ДОБРЕ: коментар пояснює бізнес-правило бібліотеки
// Якщо книгу видано після 18:00, поточний день не враховується як день прокату
if (issueTime.Hour >= 18)
{
    loanDays = Math.Max(0, loanDays - 1);
}
```

```csharp
// ПОГАНО: надлишковий коментар до очевидної властивості
// це властивість ідентифікатора
public int Id { get; init; }

// ДОБРЕ: пояснення особливості обчислення суми
// Сума обчислюється динамічно без кешування, оскільки позиції видачі
// можуть поповнюватися до моменту підписання абонемента читачем
public decimal Total() => _items.Sum(item => item.Amount);
```

### 4.2. XML-документація
- Усі публічні типи, конструктори, методи та властивості бібліотеки класів `LibraryDesk.Core` повинні мати теги `<summary>`, що лаконічно описують призначення елемента українською мовою.

## 5. Структура проєкту

Рішення організовано за дворівневою модульною структурою:

```text
LibraryDesk/
├── .editorconfig              # Машинний стандарт форматування й аналізу
├── Directory.Build.props       # Спільні властивості компіляції та аналізаторів
├── README.md                  # Загальний опис проєкту та інструкція запуску
├── CODING_STANDARD.md         # Цей стандарт кодування
├── LibraryDesk.sln            # Файл рішення .NET 8
├── LibraryDesk.Core/          # Бібліотека предметної області (Class Library)
│   ├── LibraryDesk.Core.csproj
│   └── Domain/                # Доменні сутності, моделі та перелічення
│       ├── Book.cs
│       ├── Loan.cs
│       ├── LoanItem.cs
│       ├── LoanStatus.cs
│       └── Reader.cs
└── LibraryDesk.App/           # Тонкий шар введення-виведення (Console Application)
    ├── LibraryDesk.App.csproj
    └── Program.cs
```

**Архітектурні обмеження:**
- Проєкт `LibraryDesk.Core` містить виключно бізнес-логіку й моделі; він не має жодних залежностей від консолі, UI чи сторонніх фреймворків введення/виведення.
- Виклик `Console.WriteLine`, `Console.ReadLine` або аналогічних засобів введення/виведення всередині `LibraryDesk.Core` **суворо заборонений**.
- Проєкт `LibraryDesk.App` містить виключно тонкий шар взаємодії з користувачем і посилається на `LibraryDesk.Core`.

## 6. Правила ведення комітів (Git Commit Conventions)

Повідомлення комітів формуються відповідно до конвенції **Conventional Commits**: `<тип>: <короткий опис у наказовому способі>`.

| Тип | Коли застосовується | Приклад повідомлення |
| :--- | :--- | :--- |
| `feat` | Додано нову функціональність або нову сутність | `feat: додано модель формуляра видачі Loan` |
| `fix` | Виправлено помилку в бізнес-логіці або коді | `fix: виправлено розрахунок вартості прокату` |
| `docs` | Зміни у документації (`README.md`, стандарт) | `docs: оновлено CODING_STANDARD.md` |
| `style` | Правки форматування коду без зміни логіки | `style: виправлено відступи та стиль Allman` |
| `chore` | Оновлення інфраструктури, конфігів, збірки | `chore: увімкнено аналізатори Roslyn і StyleCop` |
| `refactor`| Зміна структури коду без зміни функціональності | `refactor: оптимізовано обчислення підсумку видачі` |

Заборонено неінформативні повідомлення на кшталт: `update`, `fix`, `work`, `asdf`, `лабораторна 1`.

Кожне ключове правило стандарту підкріплене відповідним механізмом статичного аналізу (компілятор Roslyn, StyleCop Analyzers або `.editorconfig`):

| 2 | Довжина рядка до 100 символів | .editorconfig / StyleCop | `max_line_length = 100`, `SA1028` | Warning |
